What you get

  • A read node. A full, verified copy of every cast, reaction, follow and profile on Farcaster, kept in sync with the network. Anyone can run one.
  • A client. Home feed of the people you follow, profiles, threads, posting, replies, likes, recasts, follows. It also shows which app signed each cast and lets you hide or show casts by app.
  • Your own app key. The client signs with a key that belongs to you and that you added to your account yourself. Nobody in the middle can post for you, hide your feed or block your writes, as long as your node is up.

Step 0 · Get a server

curl -fsSL https://raw.githubusercontent.com/townhall-fc/townhall/main/install/provision.sh | HCLOUD_TOKEN=your_token bash
$env:HCLOUD_TOKEN="your_token"; irm https://raw.githubusercontent.com/townhall-fc/townhall/main/install/provision.ps1 | iex

What it does, in order:

  1. Uses your SSH key (~/.ssh/id_ed25519.pub, on Windows C:\Users\you\.ssh\id_ed25519.pub; created if missing) and uploads it to Hetzner, so only you can log in.
  2. Picks the cheapest server type in the location with at least 4 vCPU and 16 GB RAM.
  3. Creates a firewall that only opens SSH (22), HTTP/HTTPS for your client (80, 443) and UDP 3382, the port Snapchain nodes use to talk to each other.
  4. Creates the server with Ubuntu 24.04 and attaches a volume for the node's data: 2 TB if your account allows it, otherwise the largest it allows. 1 TB is enough (see measured).
  5. Waits until it can SSH in, then prints the next two commands with your IP filled in.

On Windows the PowerShell version does the same steps; it may ask you to press Enter twice when it creates your SSH key. Steps 1 and 2 work as they are in PowerShell.

Options: LOCATION=nbg1, SERVER_TYPE=…, VOLUME_GB=… (put them before bash; on Windows set them first, for example $env:LOCATION="nbg1"). A server is billed while it exists, see cost & cleanup.

Step 1 · Run a Snapchain read node

ssh root@YOUR_IP 'curl -fsSL https://raw.githubusercontent.com/townhall-fc/townhall/main/install/node.sh | bash'
  1. Installs Docker.
  2. Finds the disk with the most free space (your volume) and puts the node there.
  3. Downloads the official docker-compose.mainnet.yml and validators.toml from the latest Snapchain release, unchanged. That file already configures a read node (read_node = true).
  4. Starts the node. It first downloads a snapshot of the network, then replays recent blocks from peers until it catches up.
  5. Starts a small snapshot guard. On first start the node keeps every downloaded snapshot file until the very end, which is why the docs ask for 2 TB. The guard deletes each file as soon as the node has finished with it, so the first sync peaked at about 800 GB on the demo node instead of about 1.5 TB. It stops by itself when the sync is done.
  6. Installs townhall-status, a one-word command that shows how far behind each shard is.
$ ssh root@YOUR_IP townhall-status
shard 0: height 48485756  blocks behind: 1
shard 1: height 49161526  blocks behind: 0
shard 2: height 48996914  blocks behind: 1
In sync when every 'blocks behind' is in the single digits.

That is the demo node once synced. While it is still catching up, "blocks behind" counts down; on the demo node it took about 10 hours from tens of thousands to single digits.

The node answers on port 3381 with Snapchain's HTTP API. Try it on the server: curl -s localhost:3381/v1/castsByFid?fid=1 | jq '.messages[0].data.castAddBody.text'

Step 2 · Create your client

ssh root@YOUR_IP 'curl -fsSL https://raw.githubusercontent.com/townhall-fc/townhall/main/install/client.sh | bash'
  1. Clones this repository and builds the client inside a throwaway Node container.
  2. Starts Caddy, which gets an HTTPS certificate for YOUR-IP.sslip.io (a free wildcard DNS name that points at your IP; set DOMAIN=your.domain to use your own).
  3. Serves the client and forwards /v1/* to your node. The browser only ever talks to your server: same origin, no CORS, no third-party API.
  4. Starts a small service that gives shared casts a link preview: a link like /c/<fid>/<hash> shows the author and text when you paste it into Farcaster or Telegram.

Re-run the same command any time to update the client.

Using the client

Read-only

Type your username. The client resolves it to your FID on your node, loads who you follow, and builds your feed from their latest casts. Nothing is signed and nothing is sent anywhere.

Connect your account (to post)

  1. Paste your recovery phrase and press Check. The page derives your custody address from the phrase and reads your FID from the IdRegistry contract on Optimism. Nothing is sent yet.
  2. Press Add app key. The page generates a new Ed25519 keypair (your app key) and reads your current key nonce from your node (/v1/signersByFid → currentUserNonce). Your custody account then signs two EIP-712 messages: a SignedKeyRequest (which app asks for the key, here your own FID) and a KeyAdd (the key, what it may sign, how long it lives, the next nonce).
  3. It goes to your node as a message. Both signatures ride in a KEY_ADD message whose envelope is signed by the new key itself, proof that you hold it. Your node checks it and relays it like a cast. About a second later the key is active. The page clears the phrase and keeps only the app key in this browser.

Post, reply, like, recast, follow

Each action builds a protocol message, signs it with your app key in the browser, and submits the raw bytes to your node. Mentions like @alice are resolved on your node and stored as protocol mentions.

Include or exclude casts by app

Every cast is signed by an app key, and every app key records which app requested it (the app's own FID). The client looks this up on your node for each author and shows it as via farcaster, via own key and so on. Tap an app in the bar above the feed to hide or show its casts. Your choice is remembered in this browser.

Live: the network as your node sees it

Live shows every message the network accepts, a second or two after your node receives it: casts, likes, follows, profile changes, and messages pruned when someone goes over their storage limit. It reads your node's event log (/v1/events, one log per shard) and its block heights (/v1/info). Nothing here comes from anyone else's server.

Inspect a cast

Tap { } under any cast to see the protocol message behind it: its BLAKE3 hash, the Ed25519 key that signed it, which app requested that key, and a link to the raw JSON on your node. Your node stored the cast only after checking all three.

Search

Type a username or an FID. Your node resolves names with /v1/userNameProofByName; follower and following counts come from its link store.

Voters only

People who accepted the social contract in the Farcaster network vote hold a VOTE NFT on Base whose token id is their FID (contract). The client asks Base directly, ownerOf(fid), and marks those authors voted. Turn on Voters only for a feed of people who showed up. Declining minted nothing, so only "yes" is visible onchain.

Replies, from mutuals

Replies collects replies to your recent casts and casts that mention you, all read from your node. By default it shows only mutuals, people you follow who follow you back. Switch to everyone when you want the full picture.

On your phone

Open your client address and choose Add to Home Screen (Safari: Share menu; Chrome: ⋮ menu). It opens full screen like an app, still talking only to your node.

Optional: sign in without a recovery phrase

The three commands give you a client that adds its key with your recovery phrase. That is the most direct path, and it is also a phrase that controls your whole account, so use a test account. If other people will use your townhall, or you would rather not paste a phrase at all, add delegated sign-in: people approve townhall in the Farcaster app, the way they sign in to any Farcaster app, and the client gets its key without ever seeing a phrase.

ssh -t root@YOUR_IP 'curl -fsSL https://raw.githubusercontent.com/townhall-fc/townhall/main/install/signin.sh | IMPORT=1 bash'
  • It needs an app account. A key request names the app asking for the key, and that app is an FID. IMPORT=1 asks, in a hidden prompt on your server, for the recovery phrase of a spare account to act as the app; only its key is kept, in a file only root can read. Without IMPORT=1 the script makes a new key instead and registers a new FID for it once you send a little ETH on Optimism to the address it prints.
  • What people see. The sign-in page offers both ways: the Farcaster app (a QR code on desktop, a button on phones) or your own keys. Approving in the app adds the key to their account; the key itself is made in their browser and stays there.
  • What your server holds. Only the app account's key, which signs requests. No user keys, no phrases, no funds.

Concepts, in plain words

FID
Your Farcaster ID, a number. It lives in the IdRegistry contract on Optimism. Usernames, keys and every message point to it.
Custody address and recovery phrase
The Ethereum account that owns your FID. Your recovery phrase is the private key to it. Whoever has the phrase owns the account, which is why it is only used once here, locally, to add an app key.
App keys (signers)
Ed25519 keys that sign your messages. You can have many, one per app. This client adds a gasless key: a KEY_ADD message authorized by your custody address, with no transaction. Three rules come with it. Scopes: the key lists the message types it may sign (here casts, reactions, follows, profile), and can never add or remove other keys. Sliding TTL: it expires after a period of no use (up to 90 days; this client asks for the maximum), and every message it signs resets the clock. Nonces: each KEY_ADD carries a number higher than the last one for your FID, so an old authorization can't be replayed.
The older way still works: calling KeyGateway.add on Optimism, with a transaction and gas. Those onchain keys have no scopes or TTL. Your node lists both kinds at /v1/signersByFid.
Messages
Everything you do is a small signed message: CAST_ADD, CAST_REMOVE, REACTION_ADD (like or recast), LINK_ADD (follow), USER_DATA_ADD (profile). Each has a BLAKE3 hash and an Ed25519 signature, so any node can check it without trusting anyone.
Snapchain
The network that orders and stores those messages. Validators run consensus and produce blocks. Messages are split across shards by FID; shard 0 orders the others.
Read nodes vs validators
A read node follows the chain, verifies every block's signatures from the validators, stores the full state and serves the API. It does not vote and keeps no mempool. Anyone can run one; validators are a fixed set of operators.
Storage
Storage is rent, paid onchain on Optimism (the StorageRegistry contract) and counted in units. Each unit expires after a period, so rent is renewed, not bought once. A unit sets a separate limit per kind of message (casts, reactions, follows, profile data). Go over a limit and nothing fails: your oldest message of that kind is pruned to make room, which suits a timeline but means a very active account can lose old follows or casts. If your rent runs out, the network rejects new messages from you. This is how Snapchain keeps its state bounded and stops spam without per-message fees.
Check yours on your node: /v1/storageLimitsByFid?fid=YOUR_FID lists each store's limit and used, plus your units and when they expire. Rent and key events are onchain events your node indexes too: /v1/onChainEventsByFid?fid=YOUR_FID&event_type=EVENT_TYPE_STORAGE_RENT.
Usernames (fnames)
Human-readable names mapped to FIDs by a signed proof. Your node answers /v1/userNameProofByName?name=….
Clients
Apps are just programs that hold an app key for you and read from some node. The Farcaster app is one; this is another. They all see the same network.

How a cast travels

  1. You press Cast. The browser builds a CAST_ADD message with your FID, the text and mentions, hashes it, signs it with your app key, and encodes it as protobuf.
  2. It is posted to /v1/submitMessage on your server, which Caddy forwards to your read node.
  3. Your node validates it: FID exists, the key is active for that FID, hash and signature are correct, you have storage. If anything is wrong it answers with an error right away.
  4. A read node keeps no mempool, so it relays the valid message to the validators over gossip (the mempool topic).
  5. A validator includes it in a block. Your node syncs that block and the cast shows up in your feed, usually within seconds.
Read nodes and validators both accept submitMessage. A validator puts the message in its own mempool; a read node keeps no mempool, so it validates the message, gossips it on the mempool topic, and keeps nothing. That is why a 200 means "valid and relayed", not "in a block yet": if the gossip is lost under heavy load, resubmit. To confirm inclusion, read the message back from your node. Key messages (KEY_ADD, KEY_REMOVE) are routed to shard 0; casts, reactions and follows go to a message shard picked from your FID. Source: Validators vs. read nodes.

Security model

  • Treat a recovery phrase like rm -rf. It controls the whole account. Test this tutorial with a test account. In general, only paste a phrase into software you run yourself or from developers you trust, and prefer delegated sign-in (an app that holds your account approves a key for you) whenever it is available.
  • Your recovery phrase never leaves the page. It is used in your browser to sign the two key authorizations, then cleared. It is not sent to your server or stored. The only thing your node receives is the signed KEY_ADD.
  • The app key lives in this browser (local storage). Its scopes let it sign casts, reactions, follows and profile changes, never move your FID or add keys. To stop, open Settings → Revoke this key on the network: the key signs its own KEY_REMOVE, no recovery phrase needed. If you lose the device, revoke from your custody address, or just stop: an unused key expires on its own when its TTL runs out.
  • Your node's API is public through your client address: anyone can read through it (it is public data anyway) and submit validly signed messages, which your node only relays.

What "no app can ban you" means, and where it stops

Your account belongs to your custody key, not to any app. If an app hides you or shuts down, your casts, follows and profile are still on the network, and this client reads and posts them through your own node. What it does not change: blocks are produced by a small, fixed set of Snapchain validators, which in principle could refuse your messages, and the network only accepts messages from FIDs with storage rent paid. Your node makes you independent of apps and API providers, not of the protocol's own rules.

What broke when we built this

Every one of these happened on the way to the demo node. Each is now handled by the scripts, but it helps to know why.

  • Hetzner said "error during placement". The datacenter had no capacity for that server type. Step 0 now tries Falkenstein, then Nuremberg, then Helsinki.
  • Hetzner refused a 2 TB volume. New accounts are capped at 1 TB of volumes, and a limit increase was refused because the account was too new. Step 0 now falls back to the largest size allowed, and the guard below makes 1 TB enough.
  • The snapshot did not fit. Snapchain keeps every downloaded chunk, writes a full tar per shard, then unpacks it, and only cleans up at the very end. On one shard that peaks at roughly 1.5 TB. node.sh now starts a small guard that deletes chunks and tars as soon as the node is done with them, so the peak stays near 800 GB.
  • The node crash-looped with a metrics error. The official mainnet compose file points metrics at a statsd service that has to be started too. node.sh starts both.
  • A df flag mix-up (-P with --output) stopped the disk check on Ubuntu. Fixed.
  • App keys changed mid-build. The first version added the key with an Optimism transaction and asked for $1 of ETH. Snapchain now accepts gasless keys (KEY_ADD), so that step and the ETH are gone.
  • Recovery phrase confusion. The Farcaster app has two phrases: the account's recovery phrase and the wallet's. Only the account one owns your FID; the client shows the custody address and FID so you can tell before anything is signed.

Questions people ask

Where does my recovery phrase go?
Nowhere. In your browser it derives your custody address, signs the key authorization and is cleared from the page. Over the network go: your custody address (not the phrase) to a public Optimism RPC to look up your FID, and a KEY_ADD message to your node, which holds the new public key and the signatures, the same data the whole network sees. You can check this in client/src/keys.ts.
So is it safe?
The phrase does not leave your browser, but two risks are real. Whoever serves the page could change its code: on your own node that is you, building from this open repository; on someone else's townhall it is them. And a compromised computer or a malicious browser extension can read anything you type. That is why the advice is a test account, or sign-in through the Farcaster app, where no phrase is typed at all.
Which account should I use?
Inside the client, a spare account that has storage: it is the account whose phrase you paste. If you are testing this tutorial for someone, post your report from your main account; your name is what makes the report count.
What can the app key do if someone gets it?
Sign casts, reactions, follows and profile changes for that account, until you revoke it (Settings → Revoke) or it expires after 90 days unused. It cannot move your FID, change your custody address or add other keys.
Does everyone need their own server?
No. One node serves a whole community: people open a townhall and sign in, without running anything. The three commands are for people who want their own copy: communities, developers, anyone who should not depend on one operator. That any of them can is what keeps a single app from deciding who gets heard.
Why 1 TB when the Snapchain docs say 2 TB?
The network itself is about 560 GB. The extra space is for the first sync, when the node keeps every downloaded snapshot file until the end; the snapshot guard deletes each one as soon as it is used, so the demo node peaked at about 800 GB. If you keep the node for months, grow the disk as the network grows.
Can I run this from Windows?
Yes. Use PowerShell: step 0 and cleanup have Windows versions (the Windows tab above the commands), and steps 1 and 2 run as they are.
What does it cost, and how do I stop paying?
The demo node cost about $2 for its first 12 hours. Hetzner bills by the hour while the server and disk exist; the cleanup command deletes both.

Cost & cleanup

Hetzner Cloud bills by the hour, for the server and for the volume. The demo node (server plus 1 TB volume) came to about $2 for its first 12 hours, so a full test run costs a few dollars. Running it for a month is roughly a hundred-odd dollars; check current prices in the Hetzner console. A dedicated server with large disks is cheaper if you keep the node for good. Adding the app key costs nothing.

To stop paying, delete the server and the volume. This does it and asks you to confirm first:

curl -fsSL https://raw.githubusercontent.com/townhall-fc/townhall/main/install/destroy.sh | HCLOUD_TOKEN=your_token bash
$env:HCLOUD_TOKEN="your_token"; irm https://raw.githubusercontent.com/townhall-fc/townhall/main/install/destroy.ps1 | iex

Your Farcaster account is unaffected. To also revoke the app key, use Settings → Revoke in the client before you delete the server.

Testing this tutorial for someone?

Thank you. A useful test report is honest, including what failed. Please:

  1. Inside the client, use a test Farcaster account that has storage, never one that matters to you.
  2. Run the three commands from a clean machine and note the times.
  3. Once the client says the node is in sync: post a cast, follow someone, like something, and hide one app's casts with the filter.
  4. Open it on your phone too.
  5. Run the cleanup command (destroy.sh, or destroy.ps1 on Windows) so you stop paying.
  6. Post on Farcaster, from your main account, what happened, good and bad, and how long it took.

Never send your recovery phrase or Hetzner token to anyone, the author included. If you were reimbursed for server costs or your time, say so in your post.
